# Contributing Guide

Thank you for your interest in contributing to our open-source documentation website. Contributions of all kinds are welcome, whether you are fixing a typo, improving clarity, adding new content, or suggesting structural changes.

## Ways to Contribute

You can help by:

- Fixing spelling, grammar, or formatting issues
- Clarifying existing explanations
- Adding examples, tutorials, or reference material
- Reporting outdated or incorrect information
- Improving accessibility and readability
- Suggesting better navigation or organization

If you are unsure whether your idea fits, feel free to open an issue first.

## Before You Start

Please take a moment to:

- Read the existing documentation style and structure
- Search open issues and pull requests to avoid duplicate work
- Check whether there is already a discussion about the change you want to make

For larger changes, we recommend opening an issue before writing content. This helps align expectations and saves time.

## Getting Started

1. Fork the repository
2. Create a new branch for your changes
3. Make your edits
4. Preview the site locally if possible
5. Commit your changes with a clear message
6. Open a pull request

Use descriptive branch names such as `fix-installation-typo` or `add-api-auth-guide`.

## Writing Guidelines

To keep the documentation consistent:

- Write in clear, direct language
- Use short paragraphs and descriptive headings
- Prefer examples over abstract explanations
- Keep terminology consistent across pages
- Link to related pages where helpful
- Avoid unnecessary jargon

When adding technical content, make sure examples are accurate and easy to follow. If a command or code snippet is included, test it whenever possible.

## Style and Formatting

Please follow the project’s formatting conventions, including:

- Markdown structure and heading levels
- Code block formatting with language tags
- File naming patterns
- Internal linking style

If the repository includes linting or formatting tools, run them before submitting your pull request.

## Pull Request Expectations

A good pull request should:

- Clearly explain what changed
- Explain why the change is needed
- Stay focused on a single topic when possible
- Include screenshots or previews for visual changes if relevant

Be open to feedback. Reviews are a normal part of the process, and collaboration helps improve the final result.

## Reporting Issues

If you find a problem but do not want to submit a fix, open an issue. Include:

- A clear title
- A link to the affected page
- A description of the problem
- A suggestion, if you have one

## Code of Conduct

Please be respectful and constructive in all interactions. We want this project to be welcoming to contributors of all experience levels.

## Thank You

Every contribution, large or small, helps make the documentation better for everyone. We appreciate your time, effort, and ideas.
